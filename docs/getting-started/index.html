JLCA 디자인 시스템 시작하기

Core 패키지의 범위, 철학, 품질 계약과 문서를 읽는 순서를 확인합니다.

이 디렉터리는 JLCA 디자인 시스템의 활성 설계와 거버넌스 문서다. Page, Section, 제품 도메인과 application I/O는 consuming application architecture가 소유한다.

범위

디자인 시스템은 브랜드 디자인 결정, Web 환경 설정, 범용 UI와 선택적 시각 기술 capability까지만 소유한다.

이 네 디렉터리는 APPROVED CORE다. charts, carousel, maps는 실제 소비자, vendor 격리, vendor-neutral API, SSR/client와 접근성 fallback 계약이 모두 준비됐을 때 하나씩 만드는 CONDITIONAL CAPABILITY다.

Capability package는 다음 조건을 모두 만족할 때 하나씩 생성한다.

  1. 이관할 실제 제품 소비자와 대표 사용자 흐름이 있다.
  2. 큰 vendor runtime, CSS side effect 또는 별도 rendering model을 Core에서 격리해야 한다.
  3. JLCA가 소유할 public data·event·command 계약과 지원하지 않을 범위를 정의했다.
  4. SSR/client boundary, lazy loading, hydration과 실패 fallback을 정의했다.
  5. 접근성 대체 경험과 bundle·회귀 검증 기준을 정의했다.

조건을 충족하기 전에는 Core package를 만들지 않고 consuming application의 좁은 adapter로 유지한다.

설계 철학

  • Token-first: primary color를 포함한 브랜드 정체성과 light/dark 상태를 semantic token으로 먼저 설계한다.
  • Headless-first: 복잡한 접근성 interaction은 검증된 headless 구현을 사용하되 public API와 표현은 JLCA가 소유한다.
  • Branded Primitive: Primitive는 vendor wrapper가 아니라 JLCA token, variant, motion과 접근성 계약이 결합된 제품이다.
  • Quiet functional motion: 상태 변화는 짧고 단단한 모션으로 전달하되 장식적인 bounce나 layout shift를 만들지 않는다. 움직임은 motion token, transform과 opacity를 우선하고 reduced-motion과 저사양 모바일 성능을 함께 보장한다.
  • Composition over feature widget: 둘 이상의 Primitive를 조합하되 제품 용어와 application I/O를 넣지 않는다.
  • Optional capability: Chart, Carousel, Map처럼 무거운 vendor 기술은 core component와 dependency를 공유하지 않는다.
  • Product-independent: 디자인 시스템에는 제품 전용 UI, Section, Page 계층이 없다.

성공 지표

디자인 시스템의 성공은 package 수나 특정 제품의 즉시 채택만으로 판단하지 않는다. Core 자체 품질과 downstream 제품 결과를 분리해 측정한다.

Core 품질 지표:

  • catalog와 component family contract 완결성
  • public API consistency·discoverability와 compile-time invalid usage 차단
  • token 우회·source deep import·신규 Legacy import 0건
  • light/dark parity, contrast와 접근성 위반 수
  • Story 상태·theme·viewport·interaction coverage
  • SSR import/render 안전성과 dependency·bundle·CSS side effect budget
  • source·Story·저장소 문서·Notion 동기화

Downstream 결과 지표:

  • 신규 또는 개편 화면의 구현 리드타임
  • 중복 UI·스타일 구현 수와 변경 영향 파일 수
  • public root 채택률, 기존 Legacy 소비자 수와 제거율
  • 실제 제품의 UI 회귀와 접근성 위반 수

Web 의미론 계열 catalog

JLCA의 Core catalog는 외부 UI library의 component category가 아니라 Web이 제공하는 의미와 interaction model을 기준으로 나눈다.

의미론 계열소유 범위상태
Layout공간, 배치, 크기와 반응형 구조구현됨
Typography문서의 텍스트 의미와 시각 위계구현됨
Form입력, 선택, 검증과 제출검증 완료

후보 이름은 구현 목록이나 API 승인을 뜻하지 않는다. 새 Core family는 범용 의미, native semantics, token/style ownership, 접근성, SSR, type, Story, 문서와 dependency gate를 모두 닫은 뒤 catalog에 구현됨으로 기록한다. 제품 패턴과 무거운 Capability는 실제 소비 흐름이 있어야 생성한다.

Mantine을 포함한 외부 디자인 시스템은 누락된 문제와 개발 경험을 비교하는 연구 자료로만 사용한다. 외부 catalog, component 이름, prop, theme object와 runtime Provider는 JLCA의 분류나 public API를 소유하지 않는다.

의존 그래프

화살표는 consumer ─depends on→ dependency다.

Primitive는 Foundation을 runtime import하지 않는다. Foundation은 bootstrap에서 한 번 설치되고, component package는 설치된 semantic token 환경을 전제로 한다. Composition은 Capability를 import하지 않으며 Capability끼리도 서로 import하지 않는다.

현재 공개 구현

  • @jaeilnet/design-tokens
  • @jaeilnet/design-foundation/styles.css
  • @jaeilnet/design-primitives의 Layout, Typography, Form, Table과 Navigation semantic family
  • @jaeilnet/design-compositions의 InputField, Field, ChoiceField, FormGroup, Breadcrumb, Pagination

선택적 Capability는 현재 export가 없다. 소비자는 구현된 Navigation을 포함해 package root와 명시적 CSS export만 사용한다.

기본 품질 계약

  • raw brand color, arbitrary z-index, arbitrary motion을 component source에 만들지 않는다.
  • public API에 Radix, Chart.js, Swiper, Maps SDK 타입을 노출하지 않는다.
  • 각 component와 capability는 live application service 없이 fixture로 Storybook에서 렌더된다.
  • light/dark, keyboard, focus, loading/empty/error 상태를 해당 책임 계층에서 검증한다.
  • package deep import와 역방향 import를 CI에서 차단한다.

현재 gate는 독립 Tokens/Foundation/Primitives/Compositions 구조를 검증한다. Capability gate는 생성 조건을 통과한 package와 함께 추가한다.
